Scoping & Audit Requirements
Start with repository access
Scoping begins once the protocol grants the sherlock-admin GitHub account access to every repository under review.
The protocol then submits its scope through Sherlock’s scoping dashboard. This submission is used for sizing, pricing, and scheduling.
You do not need a completed, frozen codebase to book an audit. The code must be frozen three days before the audit starts.
Sizing and pricing
Final pricing and audit length are determined from the codebase at the frozen commit, using solidity-metrics and Sherlock’s audit pricing methodology.
The calculation includes:
- In-scope contracts.
- The libraries and imports used by those contracts.
Interfaces and well-known imports, mainly OpenZeppelin libraries, are excluded.
Other factors can affect the audit time, including inline assembly, highly repeated or patterned code, and integrations with other protocols.
The quote is final only at the frozen commit. Scope that grows between booking and the code freeze can change the price.

Authenticate to Sherlock AI with API keys on CloudFerro Cloud
Sherlock AI uses API keys to authenticate programmatic requests to AI models. You create API keys inside a Sherlock AI project in the control panel and then use them from your application, automation script, or backend service.
Treat every API key as a secret. Do not share it with other users, commit it to a repository, paste it into documentation, or expose it in client-side code such as browsers and mobile applications. Production requests should go through your own backend, where the key can be loaded from an environment variable or a secrets management service.
Prerequisites
Before you start, make sure that:
- You can log in to the Sherlock AI control panel after completing account and organization setup.
- You have selected the project where the API key will be created.
- Your account has permissions to manage API keys in that project.
- You know where the key will be stored after creation, because Sherlock AI shows the generated key only once.

Configuring workflows
A workflow on a search store is a named instance of a workflow class, usually the DocumentAI preset. It is configured by two JSON documents:
- parameters — overrides for the workflow’s module configuration. The workflow class defines defaults for every module. Specify only the fields that you want to change.
- schema — the JSON schema of the run input. It is currently required at creation and is planned for deprecation. See The input schema.
This page describes the parameters that DocumentAI accepts and how to manage workflows. All examples on this page were tested against a live deployment.
