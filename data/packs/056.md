There are four ways to authenticate with Firecrawl. Each one bills the team that owns the credential and gives access to the same features, so the choice depends on who holds the credential and which interface you call.
Which should I use?
If your platform creates Firecrawl accounts for its users and pays for their usage, use Firecrawl for Platforms instead.
A few REST endpoints also work with no credential at all, so you can try Firecrawl before you have a key. See No API key (keyless).
API key
Create a key in the dashboard and send it on every request asAuthorization: Bearer fc-YOUR-API-KEY. The SDKs take it as apiKey. A key has full access to the team that owns it, so keep it on your server. See Key restrictions to limit what a key can do.
Hosted MCP with an API key

[S5] https://docs.firecrawl.dev/oauth (official)
Firecrawl runs an OAuth 2.1 authorization server. Your app sends the user to Firecrawl, the user signs in and picks a team, and your app gets an access token it can use on the Firecrawl REST API in place of an API key. Usage is billed to the team the user picked. Each connection gets its own API key, created by Firecrawl and never shown to your app. The user can see and revoke the connection under Connected apps in Settings, and deleting another key in the dashboard doesn’t affect it.
If your platform creates Firecrawl accounts for its users and pays for their usage, use Firecrawl for Platforms instead. OAuth is for users who bring their own Firecrawl account. To compare OAuth with API keys and MCP sign-in, see Authentication.
Overview
Scopes
A token can do anything an API key on that team can do. Request only what you need and keep tokens on your server.

Your app needs aclient_id. There are two ways to get one, and neither needs approval from Firecrawl.

Add support for fco_ prefixed OAuth access tokens in the API gateway.
When a Bearer token starts with fco_, the auth middleware calls the
OAuth introspection endpoint to resolve it to the underlying fc- API
key, then proceeds with the normal ACUC flow.
- Add resolveOAuthToken() with Redis caching (5min max, keyed by SHA-256)
- Add OAUTH_INTROSPECT_URL and OAUTH_INTROSPECT_SECRET config vars
- fco_ tokens bypass the parseApi/UUID validation path
- Cache negative results for 60s to avoid hammering introspection
Depends on firecrawl-web#1731 (introspection endpoint) and
firecrawl-db#74 (oauth_access_tokens table).
