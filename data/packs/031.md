to access a user's Google Ads account without having to handle or store the user's
login info.

that Google supports also work with Google Ads API. However, this guide focuses on the
scenarios that are most common for Google Ads API developers.

The Google Ads API has [access levels](https://developers.google.com/google-ads/api/docs/api-policy/access-levels.md.txt) associated with the Google Cloud
project, and uses an application review process to grant various access levels.
It's important to plan and obtain the correct access levels before
productionizing your application.

A common scenario is that your application development starts with [Explorer
access level](https://developers.google.com/google-ads/api/docs/api-policy/access-levels#explorer-access), but then outgrows its quota limits over time. At
that point, you should apply for [Basic access level](https://developers.google.com/google-ads/api/docs/api-policy/access-levels.md.txt#how-to-apply-for-basic-access) or [Standard
access level](https://developers.google.com/google-ads/api/docs/api-policy/access-levels#standard-access). While Basic access applications are reviewed
automatically, the Standard access review process can take several business days
or sometimes weeks to complete, so request your Standard access level upgrade
well before you need the increased quota limits.

Google may require that your app provide certain capabilities or features as
listed in the [Required Minimum Functionality (RMF)](https://developers.google.com/google-ads/api/docs/api-policy/rmf.md.txt). When using the
Google Ads API, the RMF only applies to Google Cloud projects with Standard access
level. Make sure you review these requirements in advance to avoid additional
delays around building the necessary features in your app.

## Pricing

The Google Ads API is free to use; there are no charges for using the Google Ads API at
Explorer access, Basic access, or Standard access levels. However, if you are
subject to [Required Minimum Functionality (RMF)](https://developers.google.com/google-ads/api/docs/api-policy/rmf.md.txt), the API Review Team
audits your tool for compliance. If the audit results in a finding of
non-compliance, you may be required to pay
[non-compliance fees](https://developers.google.com/google-ads/api/docs/api-policy/non-compliance-fee.md.txt).

What can the google-ads-mcp server do?

- `GOOGLE_ADS_MCP_OAUTH_CLIENT_ID`: The OAuth 2.0 **Web application** Client ID from your API-enabled Google Cloud project for application-level OAuth authentication. Complete the following OAuth configuration steps:
  - Add the authorized redirect URIs for any AI clients that you plan to connect (such as `https://claude.ai/api/mcp/auth_callback`, `https://chatgpt.com/connector_platform_oauth_redirect`, or `https://antigravity.google/oauth-callback`).
  - Add the `https://www.googleapis.com/auth/adwords` scope to the OAuth consent screen under **APIs \& Services \> OAuth consent screen \> Data
    Access** (**Add or remove scopes**).
  - If your OAuth consent screen publishing status is set to **Testing** (the default), add the Google Accounts connecting to the MCP server as **Test users** under **APIs \& Services \> OAuth consent screen \>
    Audience** (**Test users \> + Add users**).
- `GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET`: The OAuth Client secret corresponding to your OAuth Client ID.
- `GOOGLE_ADS_MCP_BASE_URL`: The public base URL of your MCP server (for example, `https://google-ads-mcp-xyz-uc.a.run.app`). Cloud Run assigns this URL during initial deployment, so deploy withou

After deployment, configure your MCP client with the Cloud Run service URL.
Because the server enforces OAuth 2.0, your client must support the MCP OAuth
flow or supply an authorized Bearer token:

- **OAuth-enabled clients:** In clients that support MCP OAuth discovery (such as Antigravity), connecting triggers a Google sign-in prompt to grant the `https://www.googleapis.com/auth/adwords` scope (shown as `.../auth/adwords` in the Google Cloud console).
- **Third-party AI platforms (Claude, ChatGPT):** In your client's connector settings, add a custom connector pointing to your service URL with the `/mcp` path (for example, `https://google-ads-mcp-xyz-uc.a.run.app/mcp`). Select OAuth 2.0 authentication with your OAuth Client ID and Client secret, and confirm that the client's callback URI is in your OAuth client's authorized redirect URIs.
- **Clients without OAuth support:** Clients that don't support HTTP OAuth flows receive a `401 Unauthorized` HTTP status code. For those clients, use the [local stdio configuration](https://developers.google.com/google-ads/api/docs/developer-toolkit/mcp-server.md.txt#configuration) instead.

## OAuth 2.0 credentials

The Google Ads API uses OAuth 2.0 for authorizing API requests. Both OAuth 2.0 [user
authentication flow](https://developers.google.com/google-ads/api/docs/oauth/single-user-authentication) and [service
account flow](https://developers.google.com/google-ads/api/docs/oauth/service-accounts) are supported. For more details,
see [OAuth 2.0 in the Google Ads API](https://developers.google.com/google-ads/api/docs/oauth/overview.md.txt).

### Service accounts

Follow the steps to configure a [Google Cloud project for the
Google Ads API](https://developers.google.com/google-ads/api/docs/oauth/cloud-project?authpath=service_accounts). Record the
**service account email** and **service account key** . Next, follow the
common instructions in the [Service
Accounts](https://developers.google.com/google-ads/api/docs/oauth/service-accounts#account_access_setup) guide to set
up the service account to access your Google Ads account.

### User authentication

Follow the steps to [configure a Google Cloud Console project for the
Google Ads API](https://developers.google.com/google-ads/api/docs/oauth/cloud-project?authpath=user_authentication). Record
the **client ID** and **client secret** . Next, follow the [desktop app flow
instructions](https://developers.google.com/identity/protocols/oauth2/native-app#obtainingaccesstokens)
or the [web app flow
instructions](https://developers.google.com/identity/protocols/oauth2/web-server#obtainingaccesstokens)
to generate a **refresh token** and an **access token** . The `scope` to use
for Google Ads API access is `https://www.googleapis.com/auth/adwords`.

### Service accounts

When you have the **service account email** and **service account key** ,
follow the [Using OAuth 2.0 for Server to Server Applications](https://developers.google.com/identity/protocols/oauth2/service-account.md.txt#authorizingrequests)
guide to generate a **JWT claim set** , which can then be exchanged to obtain
an OAuth 2.0 access token. Make sure to select the `HTTP/REST` tab while
following the guide. The OAuth 2.0 `scope` to use for Google Ads API access is
`https://www.googleapis.com/auth/adwords`. In addition, you can skip the
`sub` parameter when constructing the JWT claim set, because the setup steps
grant the service account direct access to the Google Ads account, thus avoiding
the need to impersonate a Google Ads user.

### Projects with newly approved Basic or Explorer access levels receive an AUTHORIZATION_ERROR

- If your app uses the [user authentication workflow](https://developers.google.com/google-ads/api/docs/oauth/user-authentication.md.txt), then this is the project that owns your OAuth client ID and secret.
- If you use the [service account workflow](https://developers.google.com/google-ads/api/docs/oauth/service-accounts.md.txt), then this is the project that owns your service account.

In both these cases, you can apply for Explorer access and Basic access level
applications and get them automatically reviewed; you no longer need to work
with Google's Compliance team to complete the review process. If you need
Standard access, you need a manual review. However, you can share your approved
developer token details when applying for Standard access, so that the
Compliance team can review your new Standard access application accordingly.
